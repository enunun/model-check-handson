# 仕様と実装の対応(詳細化)

## 一言でいうと

抽象的な仕様を，具体的な実装へと詳しくしていくことを詳細化と呼ぶ．
実装が仕様の詳細化になっているとは，実装のどの実行も，仕様で許された実行に対応することである．

## 例

信号機の仕様は「赤から青に変わる」とだけ書く．
実装は，タイマーを設定し，時間が来たらランプの電流を切り替える．
実装の細かい手順(タイマーの設定，電流の切り替え)は仕様にないが，外から見れば「赤から青に変わる」に対応する．

## 仕様が実装に課す前提

仕様のアクションは，割り込まれない1回の出来事として扱われた．
実装では，1つのアクションが複数の処理(データベースの読み書き，外部への通信)になることがある．
その途中で別の処理が割り込めると，仕様では起きない状態が実装で起きる．

そのため，仕様のアクションを実装に対応させるときは，次を守る．

- 1つのアクションで変わる状態は，1つのトランザクションで変える．
- 状態を確かめる条件と，状態を変える処理を，同じトランザクションの中で行う．

Iteration 1で確かめたように，確認と引当を別の操作にすると，仕様にない割り込みが起きる．
仕様がどこを1回の操作としたかは，実装への要求である．

## なぜ必要か

モデル検査で仕様の性質を確かめても，その結果が実装に当てはまるのは，実装が仕様の詳細化になっているときだけである．
仕様と実装の対応を決め，それを守る実装にすることで，モデル検査の結果を実装の品質に結びつけられる．

## テストとの違い

テストは，実装の個々の振る舞いを確かめる．
詳細化は，実装の実行全体が仕様の実行に対応することを求める．
モデルベーステストは，その一部をテストとして確かめる方法である．

## よくある誤解

- 実装が仕様より細かい手順を持つことは，問題ではない．外から見た状態の変化が，仕様のアクションに対応していればよい．
- トランザクションを使えば，すべての割り込みが防げるわけではない．外部システムへの通信はトランザクションに含められないので，仕様でも別のアクションとして書いた．

## Quintでの書き方

仕様のアクションごとに，実装の関数を1つ対応させる．
対応は，モデルベーステストのアクションの対応表として書く．
