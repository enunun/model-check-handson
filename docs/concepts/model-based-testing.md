# モデルベーステスト

## 一言でいうと

仕様(モデル)から実行の手順を自動で作り，同じ手順を実装にも流して，実装が仕様と同じ状態を通るかを確かめるテストである．

## 流れ

1. 仕様からトレース(状態とアクションの列)を多数生成する．
2. トレースの各ステップのアクションを，実装の対応する関数の呼び出しに変える．
3. 呼び出しのあとの実装の状態を，トレースの次の状態と比べる．
4. 一致しなければ，仕様と実装がずれている．

## 例

信号機の仕様から，「赤→青→黄→赤」というトレースを作る．
実装の信号機を赤で始め，`toGreen`，`toYellow`，`toRed`を順に呼び，そのたびに色を仕様の状態と比べる．
実装の`toYellow`が赤に変えてしまう誤りがあれば，2つ目のステップで不一致になる．

## なぜ必要か

モデル検査は仕様を調べる．
仕様の抜けを直しても，実装がその決定どおりに作られているとは限らない．
モデルベーステストは，仕様で決めた振る舞いが実装に反映されているかを確かめる．

手順は仕様から自動で作られるので，テストを書く人が思いつかない順番も実装に流れる．
仕様を直したら，テストの手順も自動で変わる．

## 環境と実装を分ける

トレースには，実装が担当しないアクション(外部システムの振る舞いなど)も含まれる．
それらは実装を呼ばずに読み飛ばし，実装が持つ状態変数だけを比べる．
どの状態変数とアクションが実装の担当かを，先に決めておく．

## 網羅を確かめる

トレースはランダムシミュレーションで作るので，すべてのアクションが現れるとは限らない．
現れなかったアクションの実装は，テストされない．
すべてのアクションがトレースに現れることを，テストで確かめる．現れなければ，トレースの本数や長さを増やす．

## テストとの違い

普段のテストは，手順と期待する結果を人が書く．
モデルベーステストでは，手順と期待する結果の両方を仕様が与える．
人が書くのは，トレースのアクションと実装の関数の対応だけである．

## よくある誤解

- トレースで実装が仕様と一致しても，実装が正しいとは限らない．トレースは，仕様で起きうるアクションだけを流す．仕様では起きない呼び出しを実装が受け付けてしまう誤りは，見つからない．
- モデルベーステストは，モデル検査の代わりではない．仕様そのものの誤りは，モデル検査で見つける．

## Quintでの書き方

`quint run --mbt --out-itf`でトレースをITF形式のJSONに出力する．
