# 抽象化

## 一言でいうと

仕様に書くことと書かないことを選ぶことである．
調べたい問いに関係する部分だけを書き，関係しない細部は省くか，単純なものに置き換える．

## 例

エレベーターの扉の安全性を調べるとき，次のように抽象化する．

| 実際のシステム | 仕様 |
| --- | --- |
| 地上1階から地上20階 | 1階と2階の2つの階 |
| 移動にかかる秒数 | 「移動中」という1つの状態 |
| 乗客の体重と人数 | 書かない(扉の安全性に関係しない) |

扉が移動中に開くかという問いには，階の数や秒数は関係しない．
2つの階で起きない誤りは，20の階でもほとんどの場合起きない．

## このハンズオンの抽象化

これまでの仕様でも，多くのことを省いてきた．

- 顧客は2人，注文は2件，商品は2種類，在庫は1個か2個．
- 時間は「時間切れが起きうる」という出来事だけで表した．
- 決済代行サービスと配送システムの内部の処理は書かず，外から見える結果だけを書いた．
- 再試行の回数には上限を設けた．

## 抽象化を選ぶときの問い

- 調べたい性質は何か．その性質に関係する状態変数とアクションはどれか．
- 省いた細部によって，起きうることが減っていないか．たとえば，決済が必ず成功すると書くと，失敗の場合を調べなくなる．
- 数を小さくしても，調べたい場面(同じ商品を2件の注文が取り合うなど)は起きるか．

## なぜ必要か

実際のシステムをそのまま書くと，状態の数が多すぎて検査が終わらない．
抽象化によって状態の数を減らすと，検査できるようになる．
一方で，問いに関係する部分まで省くと，誤りを見逃す．

## テストとの違い

テストでは，実際の値や実際のデータを使う．
仕様では，値の種類を最小限にして，その代わりにすべての組み合わせを調べる．

## よくある誤解

- 抽象化は，仕様をあいまいにすることではない．省いたものは省いたと決め，残したものは正確に書く．
- 数を小さくした仕様で性質が成り立っても，大きな数で成り立つ証明にはならない．ただし，多くの誤りは小さな数で見つかる．[状態爆発と小スコープ仮説](state-explosion-and-small-scope.md)を参照する．

## Quintでの書き方

定数(`pure val`)で数や組み合わせを決め，関数(`pure def`)で仕様の中の計算に名前を付ける．
