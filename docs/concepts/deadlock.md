# デッドロック

## 一言でいうと

どのアクションの条件も満たされず，それ以上1つも遷移できない状態である．

## 例

2人の作業者が，それぞれ道具Aと道具Bを1つずつ持ち，相手の道具を待っている場面を考える．
どちらも相手が道具を手放すまで何もできず，作業は永遠に進まない．
これは，望ましくないデッドロックである．

一方で，すべての注文の処理が終わり，することがなくなった状態も，遷移できない状態である．
これは，仕事が終わった正常な状態である．

## なぜ必要か

モデル検査の道具は，遷移できない状態を見つけると，それを報告する．
報告された状態が，望ましくないデッドロックなのか，正常な終わりなのかを見分ける必要がある．

- 正常な終わり：すべての注文が「引当済み」や「お断り」などの最終的な状態になっている．
- 望ましくないデッドロック：処理の途中の状態(「確認済み」など)のまま，どの遷移も起きない．

## このハンズオンでの扱い

`quint verify`(Apalache)は，遷移できない状態をデッドロックとして違反にする．
このハンズオンの仕様では，すべての注文が決着した状態は正常な終わりである．
そこで，`quint verify`を直接使うときは，`tools/apalache.json`でデッドロックの検査を切る．
`mise run verify`はTLC(`--backend=tlc`)で検査する．QuintはTLCを呼ぶときにデッドロックの検査を切るので，指定は要らない．

処理の途中で止まってしまう問題は，デッドロックの検査ではなく，Iteration 4で扱う活性の性質で調べる．
活性の性質では，「途中の状態の注文は，いずれ最終的な状態になる」ことを直接書く．

## テストとの違い

テストでは，止まってしまう順番を狙って書かなければ，デッドロックに気づかない．
モデル検査は，到達できるすべての状態について，遷移できるかどうかを調べる．

## よくある誤解

- デッドロックは，並行処理のロックの取り合いだけで起きるものではない．条件の書き方を誤ると，どのアクションも起きなくなる．
- 遷移できない状態がすべて誤りではない．仕事が終わった状態は，遷移できなくてよい．

## Quintでの書き方

`quint verify`を直接使うときは，`--apalache-config`でデッドロックの検査を切る．

```sh
quint verify shop.qnt --invariants invStockNonNegative --apalache-config=../../../tools/apalache.json
```

構文は[Iteration 1の構文の解説](../quint/iteration-1.md)を参照する．
