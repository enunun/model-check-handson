# インターリーブと原子性

## 一言でいうと

複数の処理が同時に進むとき，それぞれの手順が交互に入り混じって実行されることをインターリーブと呼ぶ．
途中にほかの処理が割り込めない，ひとまとまりの操作を原子的な操作と呼ぶ．

## 例

座席予約で，2人が同じ席を予約する場面を考える．
予約の処理が「空席を確かめる」と「席を確保する」の2つの手順からなるとき，次の順番がありうる．

| 順番 | Aさんの処理 | Bさんの処理 | 席の状態 |
| --- | --- | --- | --- |
| 1 | 空席を確かめる(空いている) | | 空き |
| 2 | | 空席を確かめる(空いている) | 空き |
| 3 | 席を確保する | | Aさん |
| 4 | | 席を確保する | Bさん(Aさんの予約が上書きされる) |

どちらの処理も，1人で動かせば正しく動く．
問題は，2つの処理の手順が交互に実行されたときにだけ起きる．

## なぜ必要か

仕様のアクションは，1つずつ原子的に起きる．
1つのアクションの中は，割り込まれない．
そのため，実際には割り込まれうる処理を1つのアクションにまとめて書くと，割り込みで起きる問題を検査できない．

仕様を書くときは，実際のシステムで割り込まれうる境目ごとに，アクションを分ける．
たとえば，確かめる処理と書き込む処理が別のリクエストやトランザクションで行われるなら，別のアクションにする．

## 原子性で問題を解く

インターリーブで起きる問題は，次のいずれかで解く．

- 確かめる処理と書き込む処理を，1つの原子的な操作にする(データベースのトランザクション，条件付きの更新など)．
- 書き込む時点で，条件をもう一度確かめる．条件を満たさなければ失敗として扱う．

どちらを選ぶかは，要求の決定事項になる．

## テストとの違い

インターリーブの問題を単体テストで再現するには，処理の途中で止めて別の処理を差し込む必要があり，難しい．
モデル検査では，アクションの境目で起きうるすべての割り込みを調べる．

## よくある誤解

- 「同時に起きる確率は低い」は，問題がないことの理由にならない．利用者が増えれば，低い確率でも必ず起きる．
- 1つのアクションを細かく分けるほどよいわけではない．実際に割り込まれうる境目だけで分ける．

## Quintでの書き方

割り込まれうる手順ごとに`action`を分け，`step`で非決定的に選ぶ．
